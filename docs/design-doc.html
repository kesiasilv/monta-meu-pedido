1 · Sobre este documento

Que tipo de documento é este

Este é um design doc (documento de design técnico), o formato que times de engenharia como Google, Uber e o próprio iFood usam antes de construir um sistema. Ele junta quatro práticas comuns em projetos de IA:

PráticaPara que serveOnde aparece aqui
Design docRegistra o problema, os objetivos, o que fica de fora e como o sistema será construído, antes de escrever o códigoSeções 2 a 6, 9 e 10
ADR (Architecture Decision Record)Registra cada decisão importante com contexto, alternativas e consequências. Quando uma decisão muda, cria-se um ADR novo em vez de apagar o antigoSeção 12
Datasheet for Datasets (Gebru et al., 2018)Documenta de onde vieram os dados, como foram rotulados e suas limitaçõesSeção 7
Model Card (Mitchell et al., 2019)Documenta o modelo: uso pretendido, métricas, limitações e vieses. O Hugging Face usa esse formatoSeção 8

"Documento de visão" e PRD são documentos de produto: descrevem o que construir e por quê, do ponto de vista do usuário. Para a trilha Engineer, o design doc é mais adequado, porque também descreve como construir e como provar que funciona.

Como usar este documento para decidir

Antes de qualquer decisão no código, responda:

  1. Isso ajuda a cumprir algum objetivo?
  2. Isso fere algum não-objetivo? Se sim, não faça.
  3. Isso contradiz algum ADR? Se sim, escreva um ADR novo explicando por que mudou, ou não faça.
  4. Isso segue os padrões de engenharia e mantém os testes passando?
  5. A entrega cumpre a definição de pronto?

Se as cinco respostas forem boas, a decisão está de acordo com o documento.

2 · Contexto e problema

Por que este sistema existe

Escolher comida em um app de delivery exige cruzar várias condições ao mesmo tempo: quanto posso gastar, o que não posso comer, quanto tempo posso esperar e do que estou com vontade. Hoje o cliente faz isso sozinho, filtrando e comparando dezenas de pratos.

Problema: dado um pedido em linguagem natural, montar um carrinho de um único restaurante que respeite orçamento, restrições alimentares e tempo de entrega, e explicar a escolha.

Dificuldade técnica central: saber se um prato respeita uma restrição exige entender a descrição e os ingredientes. Um LLM faz isso bem, mas é caro e lento para rodar em milhares de pratos. A pergunta de pesquisa do projeto vem daí: um modelo pequeno ajustado consegue substituir um LLM nessa classificação?

3 · Objetivos e não-objetivos

O que entra e o que fica de fora

Objetivos

  • O1. Treinar e publicar um classificador multi-label de 7 tags alimentares em português.
  • O2. Comparar com evidência três abordagens: baseline clássico, modelo ajustado e LLM zero-shot.
  • O3. Integrar o modelo num workflow com LLM que monta pedidos respeitando regras críticas.
  • O4. Entregar código com qualidade de produção: tipado, testado, com CI e reprodutível.
  • O5. Documentar tudo (README, relatório técnico, model card e datasheet) e deixar uma demo pública.

Não-objetivos

  • Não usa dados reais do iFood nem faz scraping de cardápios.
  • Não tem login, pagamento ou histórico de usuário.
  • Não usa agente autônomo nem multiagente (ver ADR-001).
  • Não tem automações de Builder: n8n, Telegram, dashboard de insights.
  • Não serve para alergias graves. É uma demonstração.
  • Não otimiza infraestrutura (Kubernetes, filas, escala).

6 · Workflow e contratos de dados

O caminho de um pedido

A sequência é fixa e decidida pelo código. O LLM entra só em dois passos: para entender o texto do cliente e para escrever a explicação.

flowchart TD
  IN["Mensagem do cliente"] --> P1["1. Interpretar
LLM gera JSON"]
  P1 --> V{"JSON válido
e completo?"}
  V -- "falta orçamento" --> Q["Pergunta ao cliente"]
  V -- "sim" --> P2["2. Buscar
busca semântica + filtros"]
  P2 --> P3["3. Filtrar restrições
seu BERTimbau"]
  P3 --> E{"Sobrou
algum prato?"}
  E -- "não" --> NADA["Avisa e sugere
relaxar um critério"]
  E -- "sim" --> P4["4. Montar carrinho
código, dentro do orçamento"]
  P4 --> P5["5. Explicar
LLM escreve o porquê"]
  P5 --> OUT["Resposta: carrinho + explicação"]
PassoQuem fazEntrada → saídaProteção contra erro
1. InterpretarLLMTexto → PedidoInterpretadoSaída em JSON validada pelo Pydantic. Se o JSON vier inválido, tenta uma vez; se falhar de novo, pede ao cliente que reformule. Sem orçamento, o código pergunta
2. BuscarCódigodescricao_livre + filtros → até 30 pratosPreço máximo e tempo máximo aplicados como filtro no ChromaDB, nunca pelo LLM
3. Filtrar restriçõesSeu modeloCandidatos → só os que têm todas as tags exigidasLimiar por tag ajustado na validação. Na dúvida, o prato sai
4. Montar carrinhoCódigoCandidatos + orçamento → CarrinhoTesta todas as combinações de 1 principal + 0 ou 1 extra do mesmo restaurante, descarta as que passam do orçamento e escolhe a de maior relevância na busca
5. ExplicarLLMCarrinho + pedido → textoO LLM recebe o carrinho fechado. O código confere que o texto só cita pratos do carrinho; se citar outro, usa uma explicação padrão gerada em código

Restrição e preferência não são a mesma coisa

As 7 tags se dividem em dois grupos com comportamentos diferentes no workflow:

  • Restrições (obrigatórias): vegano, vegetariano, sem_lactose, sem_gluten. Um prato que não tem a tag exigida sai no passo 3.
  • Preferências (desejáveis): fit, picante, doce. Só aumentam a pontuação do prato no passo 4, sem eliminar ninguém.

Contratos de dados

Cada passo recebe e devolve objetos Pydantic. Isso documenta o formato, valida em tempo de execução e permite testar cada passo sozinho.

class Restricao(StrEnum):
    VEGANO = "vegano"; VEGETARIANO = "vegetariano"
    SEM_LACTOSE = "sem_lactose"; SEM_GLUTEN = "sem_gluten"

class Preferencia(StrEnum):
    FIT = "fit"; PICANTE = "picante"; DOCE = "doce"

class PedidoInterpretado(BaseModel):          # saída do passo 1
    orcamento: float | None = Field(None, gt=0)
    restricoes: list[Restricao] = []
    preferencias: list[Preferencia] = []
    descricao_livre: str                      # ex.: "algo leve e refrescante"
    tempo_max_min: int | None = Field(None, gt=0)

class Prato(BaseModel):
    id: str; restaurante_id: str; nome: str; descricao: str
    ingredientes: list[str]; preco: float
    tipo: Literal["principal", "bebida", "sobremesa"]

class Carrinho(BaseModel):                    # saída do passo 4
    restaurante_id: str; itens: list[Prato]
    subtotal: float; taxa_entrega: float; total: float
    tempo_entrega_min: int

class Resposta(BaseModel):                    # saída da API
    status: Literal["ok", "precisa_info", "sem_opcao"]
    carrinho: Carrinho | None = None
    mensagem: str

Camada de LLM trocável

class LLMClient(Protocol):
    def gerar_json(self, system: str, user: str, schema: type[T]) -> T: ...
    def gerar_texto(self, system: str, user: str) -> str: ...

# mmp/llm/__init__.py
def criar_cliente() -> LLMClient:
    match settings.llm_provider:          # vem do .env
        case "gemini": return GeminiClient(settings.gemini_model)
        case "claude": return ClaudeClient(settings.claude_model)

O workflow só conhece LLMClient. Nos testes, entra um FakeLLMClient que devolve respostas fixas, sem chamar API nenhuma.

Definição de cada tag

Essas definições vão no prompt de geração e no dataset card. Sem elas, o rótulo vira opinião.

TagTipoDefinição
veganorestriçãoNenhum ingrediente de origem animal: carne, peixe, ovo, leite, mel
vegetarianorestriçãoSem carne, peixe ou frutos do mar. Pode ter ovo e laticínios
sem_lactoserestriçãoSem leite e derivados: queijo, manteiga, creme de leite, iogurte, leite condensado
sem_glutenrestriçãoSem trigo, cevada, centeio ou aveia comum. Massa, pão e empanados contam como glúten
fitpreferênciaLeve: grelhado, cozido ou cru, sem fritura, até ~600 kcal estimadas
picantepreferênciaPimenta ou molho apimentado como característica do prato
docepreferênciaSabor predominante doce: sobremesas e bebidas adoçadas

Limitações conhecidas

Os dados são sintéticos: refletem o que o Gemini acha que é um cardápio brasileiro, com menos variedade e menos erros de digitação que cardápios reais. Os rótulos vêm do mesmo LLM que serve de baseline, o que pode favorecê-lo na comparação. As duas limitações vão no relatório.

9 · Avaliação

Como provar que funciona

O laboratório não atende cliente nenhum. É um script (make eval) que importa as mesmas peças do produto, roda casos de teste e gera os números do relatório e do currículo.

flowchart LR
  TS[("Conjunto de teste
nunca usado antes")] --> B["Baseline TF-IDF"]
  TS --> M["Seu BERTimbau"]
  TS --> Z["LLM zero-shot"]
  B --> MET["F1, custo e latência"]
  M --> MET
  Z --> MET
  CA[("30 pedidos de teste
com regras conhecidas")] --> W["Workflow completo"]
  W --> CHK["Checagem automática
orçamento, restrição e tempo"]
  MET --> R["RELATORIO.md"]
  CHK --> R

Pergunta A: o modelo vale a pena?

  • F1 micro, F1 macro e F1 por tag
  • Custo por 1.000 pratos: tokens × preço da API para o LLM; ~0 para os locais
  • Latência média por prato
  • Matriz de erros por tag e 10 exemplos de erro comentados

Pergunta B: o workflow respeita as regras?

  • 30 casos: 10 simples, 10 com várias restrições, 5 sem orçamento, 5 impossíveis
  • % que respeita orçamento, restrições e tempo
  • % de status correto (ok, precisa_info, sem_opcao)
  • Latência p50 e p95

Regras do protocolo

  • O conjunto de teste só é usado uma vez, no final. Toda escolha (limiar, épocas, prompt) é feita na validação.
  • Os três classificadores recebem exatamente os mesmos pratos.
  • Cada resultado é salvo em evals/resultados/ com data, versão do modelo e seed.

12 · Decisões registradas

ADRs

Clique para abrir. Quando uma decisão mudar, crie um ADR novo que substitui o antigo, e marque o antigo como "substituído". No repositório, cada ADR vira um arquivo em docs/adr/.

ADR-001Workflow em vez de agente autônomo
Contexto
A sequência de passos é sempre a mesma e as regras (orçamento e restrições) são críticas. Um agente decide os passos em tempo de execução e pode pular uma checagem.
Decisão
O código define a ordem dos 5 passos. O LLM só interpreta o pedido e escreve a explicação.
Alternativas
Agente com tool calling; multiagente (intérprete, montador, revisor).
Consequências
Comportamento previsível, testável e mais barato. Menos flexível para pedidos fora do padrão. Os passos 2 a 4 continuam utilizáveis como ferramentas numa versão com agente.
ADR-002Classificador próprio em vez de LLM para as restrições
Contexto
Classificar cada prato com um LLM a cada pedido custa caro e adiciona latência.
Decisão
Fine-tuning do BERTimbau, um modelo em português pequeno o suficiente para rodar em CPU.
Alternativas
LLM zero-shot; regras por palavra-chave; modelo multilíngue (XLM-R).
Consequências
Custo quase zero por classificação. Precisa de dados rotulados e de retreino se as tags mudarem. A troca é medida na avaliação.
ADR-003Gemini como LLM padrão, atrás de uma interface
Contexto
O projeto precisa custar zero e não pode ficar preso a um provedor.
Decisão
Gemini pelo plano gratuito do Google AI Studio, acessado só pela interface LLMClient.
Alternativas
Claude ou GPT direto; modelo aberto local (Ollama).
Consequências
Trocar de provedor é mudar o .env. O plano gratuito tem limite de requisições, então a geração de dados roda em lotes com pausa.
ADR-004Dados sintéticos com revisão humana por amostragem
Contexto
Não há dataset público de cardápios brasileiros rotulados, e scraping de apps de delivery fere os termos de uso.
Decisão
Gerar com LLM, validar com Pydantic e revisar 50 itens à mão para medir a qualidade dos rótulos.
Alternativas
Rotular dados reais à mão (inviável em um dia); scraping.
Consequências
Dados limpos demais e possível vantagem para o LLM na comparação. Documentado como limitação.
ADR-005ChromaDB local para a busca semântica
Contexto
São ~400 pratos. Não há necessidade de banco vetorial gerenciado.
Decisão
ChromaDB em disco com o modelo de embeddings paraphrase-multilingual-MiniLM-L12-v2, que é leve e entende português.
Alternativas
FAISS; Pinecone; busca só por palavra-chave.
Consequências
Zero infraestrutura e filtros por metadado (preço, tempo) prontos. Não escala para milhões de pratos, o que é um não-objetivo.
ADR-006Montador por busca exaustiva em código
Contexto
O carrinho precisa respeitar o orçamento sempre.
Decisão
Agrupar os candidatos por restaurante, testar todas as combinações de 1 principal + 0 ou 1 extra, descartar as que passam do orçamento ou do tempo e escolher a de maior pontuação (relevância da busca + bônus por preferência atendida).
Alternativas
Deixar o LLM escolher; algoritmo guloso; programação linear.
Consequências
Com no máximo 30 candidatos são menos de 1.000 combinações, então roda instantâneo e o resultado é sempre correto. Não serve para carrinhos grandes, o que é um não-objetivo.

Contexto

Decisão
Gradio hospedado no HF Spaces, ao lado do modelo e do dataset.
Alternativas
Streamlit Community Cloud; dashboard com insights; bot no Telegram via n8n.
Consequências
Modelo, dataset e demo ficam juntos no perfil do Hugging Face. Sem dashboard analítico, que fica para a versão 2.
